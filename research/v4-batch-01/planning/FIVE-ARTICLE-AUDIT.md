# V4 — Five-article audit and executor decision queue

**Planning/review handoff, not installed policy.** Baseline: AI-skills `research/v4-composability-batch-01`. For authoritative behavior inspect current `AGENTS.md`, `instructions/orchestration-contract.md`, relevant first-party/vendor skills and `docs/records/egm-mechanics-audit.md` before edits. This research record preserves V3 and does not enable optional AI Skills delegation mode.

## Executive conclusion
**Preserve V3's two owner-controlled workflow paths (Full Feature / Change-Bug), explicit optional delegation-mode selection, role ownership, HDC one-active-feature boundary, risk-based verification, independent review, and recoverable working artifacts.** Let the orchestrator organize execution *within* these boundaries. Avoid new skill names, central registries, global daemons, CI/PR permissions or redundant reviewer agents.

**Statuses:** `EXECUTOR-READY-CANDIDATE` means the user asked for beneficial improvements to be logged for an independent implementation model to validate and implement *on its authorized research branch only*, if the real delta is demonstrated. It is **not** a claim of approval to change master, installations or HDC live services. `PRESERVE` means no implementation. `OWNER-CHOICE` means a material behavior/authority decision needs the owner. `INVESTIGATE` means don't implement until a real gap is found.

The executor must **inspect, challenge and decide**: (a) already covered → mark no-op, (b) useful minimal compatible change → implement on research branch with checks and evidence, (c) broader/contradictory or risky change → write a concise pushback and seek owner decision. No blind edits; no changes to stable branches or installed environments.

## Executor protocol — mandatory intellectual independence, not new production policy
1. Read canonical current sources and the cited original external source. Confirm baseline branch, working tree, existing implementation and existing EGM/review/friction improvements; avoid rewriting previously fixed items.
2. For each `EXECUTOR-READY-CANDIDATE`, return disposition: **already present/no-op**, **implement smallest compatible delta**, **push back (evidence / smaller alternative)**, **owner decision needed (why)** or **unverified / blocked**. Avoid inventing defects to justify activity.
3. Implement only the smallest compatible improvements **on the three research branches** after source review. One mutation owner per repo. Do not add new stages, mandatory skills, repo-wide docs, model routes, new approval policies, external plugins, accounts or production automation.
4. Existing `npm test`, scoped tests and baseline comparisons as appropriate. Keep user outcome acceptance separate from test assertions and source audits. Preserve failed attempts and preexisting failures.
5. Each repo keeps one concise `research/v4-batch-01/results/IMPLEMENTATION-CHALLENGE.md` with ID, status, actual changed files/lines, exact run commands/results, source refs, objections, recommended owner decision if any. Push research branches only if task explicitly authorizes push; never merge.
6. Findings about HDC stay in HDC, provider-specific fixes in AI-plugins, generic review/planning/test/coordination semantics in AI-skills. Challenge a proposed different owner.
7. Do not add chronology to canonical instruction files; amend authoritative rule in place only when approved. The user chose **two workflows and explicit delegation mode activation**, never auto-select others.
