# Plan debate

Debate a plan before implementation. The working output is **one session scratchpad**, not an approved design or a new document of record. A clean debate is a go-ahead signal, not proof of safety. The owner decides whether the plan is ready and resolves disagreements; reviewers do not implement changes during review.

## Set up the session

1. Read the project's instructions and any scratchpad/closeout profile. Identify the proposed change, scope, draft author, any challenge reviewer, optional independent reviewer, and owner. The active orchestrator is the draft author by default; use another author/reviewer only when the owner explicitly directs that delegation for this task. State participants and roles before dispatch; do not present one agent's self-review as independent debate. Use routes only with the owner's authorization and project rules. If a requested reviewer is unavailable, disclose that and ask how to proceed; never silently substitute or claim a debate occurred.
2. Gather the ticket, requirements, slides, existing design/LLD, relevant project documents and source files needed to test important claims. Ask for missing or inaccessible material rather than treating a summary as proof. Follow project rules for sensitive material and external transmission: include only necessary, authorized excerpts, never secrets or customer data. Record provenance (file and line/section, slide number, ticket item, or a distinctive label for pasted text), and note which sources were actually inspected versus only reported by someone else.
3. Choose **one working scratchpad**. Reuse a project's designated session scratchpad only if its profile permits this debate content and reuse; preserve its format and existing entries. Otherwise create a separate temporary working file outside project repositories, at a location agreed with the owner when project rules do not specify one. Do not overwrite another session's notes. The orchestrator is the scratchpad's **only writer**. Owner-authorized delegates may read it for review or implementation, but must never edit, append, reformat, or delete it. Grant read-only access where the host supports it; if it cannot enforce that boundary, give the delegate a separate immutable copy/snapshot and withhold the live file's writable path. Delegates return findings or proposed updates in their response, or create a separate `minipad.md` only in an explicitly authorized output location; the orchestrator alone decides what to merge into the scratchpad. Never claim a host-enforced access guarantee without evidence. The scratchpad may hold task notes, source references and necessary excerpts, grill answers, findings, a draft plan, reviewer comments and responses, decisions, and unresolved questions. It is a working draft, not a replacement for `handoff` or `session-closeout`. Do not create a standalone implementation-brief artifact.

## Debate in the scratchpad

1. **Draft:** the author records the goal, scope and exclusions, constraints, proposed steps or slices, dependencies, alternatives and tradeoffs, assumptions, risks, verification/rollback ideas where relevant, and open questions. Cite consequential factual premises to source locations. Mark unknowns and proposed choices as such; do not convert grill answers or secondhand summaries into verified facts.
2. **Challenge:** give the declared challenge reviewer read-only access to the scratchpad when the host can enforce it, plus only necessary source material to verify important claims. Otherwise give it an immutable plan snapshot and source excerpts, not the live writable file. Ask for concrete counterexamples, missing dependencies, conflicting requirements, unsafe sequencing, and untested assumptions. Require a separate Markdown response containing numbered findings, each with its claim, category (**Observed contradiction**, **Concern**, or **Unsupported assertion**), source reference or explicit evidence gap, impact, and proposed check or change. No fabricated citations or invented test results. A reviewer unable to verify a material premise must say so rather than endorsing it.
3. **Independent check (if available):** give the independent reviewer read-only scratchpad access only if the host enforces it; otherwise provide an immutable plan snapshot and, if useful, the other reviewer's returned Markdown report plus necessary source excerpts. Ask it to assess the plan and prior findings, including whether objections are supported or overstated and what was missed. Require a separate Markdown response (or authorized `minipad.md`) with its findings and limits; do not collapse its comments into the first reviewer's voice. Reviewers may be dispatched in parallel when the owner has authorized both. The orchestrator may relay outputs for a response round without taking a substantive side; it remains the sole scratchpad writer and records attribution. Disclose if a pass was skipped or could not verify sources.
4. **Response:** the plan author returns an answer for each finding by ID—accept and revise, reject with evidence, or leave open with the missing check/decision. By default, the orchestrator is the author and writes its response to the scratchpad. If authorship was delegated, collect the author's separate Markdown response and have the orchestrator record it. Preserve returned reports and attribution; do not erase criticism or silently mark disagreement resolved. If the owner wants reviewers to respond to each other, the orchestrator relays the relevant immutable text and collects separate Markdown replies, then records them. If a revision changes a material premise, send only the revised snapshot and necessary evidence to the affected reviewer when authorized. Stop cycling when the owner has enough to decide; do not manufacture consensus.
5. **Owner arbitration:** present the revised draft and a short ledger of accepted changes, contested findings, unsupported claims, unverified sources, and unresolved risks/questions. Ask the owner to decide contested choices explicitly; record each decision and who made it. Anything not resolved remains open with an owner/next check, not an implicit approval. State which reviewers actually participated and what they inspected. Only the owner can give the go-ahead; even a review with no blockers does not prove the plan safe.

## Stop boundary

Leave the draft, exchanges, decisions, and unresolved items together in the scratchpad for later use. Do **not** apply the draft to project documents, approve an LLD, implement code, create a PR, or write a separate implementation brief as part of this skill. A later authorized workflow can use the settled plan as input to a slice-scoped delegate brief; `session-closeout` handles durable write-backs and `handoff` handles a specific next task. For one-shot plan feedback use a plan-review workflow instead; `two-axis-review`, `debate-review`, and `babysit-pr` concern code changes or PRs, not this pre-implementation exchange.
