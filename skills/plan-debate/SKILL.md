# Plan debate

Debate a plan before implementation. The working output is **one session scratchpad**, not an approved design or a new document of record. A clean debate is a go-ahead signal, not proof of safety. The owner decides whether the plan is ready and resolves disagreements; reviewers do not implement changes during review.

## Set up the session

1. Read the project's instructions and any scratchpad/closeout profile. Identify the proposed change, scope, draft author, available challenge reviewer, optional independent reviewer, and owner. State the participants and their roles before dispatching a review; do not present one agent's self-review as independent debate. The intended live sequence, when connected, is: Sol drafts, Gemini challenges with evidence, an independent Sonnet or Opus reviewer checks the draft **and** the challenge, the author responds, and the owner arbitrates. These are roles for this workflow, not required CLI names or model pins. Use available routes only with the owner's authorization and project rules. If the challenge reviewer is unavailable, disclose that and ask the owner how to proceed; do not claim a debate occurred. If Sonnet/Opus access is unavailable, disclose the missing independent pass and continue without it if the owner wants; never silently substitute another reviewer or claim that pass was performed.
2. Gather the ticket, requirements, slides, existing design/LLD, relevant project documents and source files needed to test important claims. Ask for missing or inaccessible material rather than treating a summary as proof. Follow project rules for sensitive material and external transmission: include only necessary, authorized excerpts, never secrets or customer data. Record provenance (file and line/section, slide number, ticket item, or a distinctive label for pasted text), and note which sources were actually inspected versus only reported by someone else.
3. Choose **one working scratchpad**. Reuse a project's designated session scratchpad only if its profile permits this debate content and reuse; preserve its format and existing entries. Otherwise create a separate temporary working file outside project repositories, at a location agreed with the owner when project rules do not specify one. Do not overwrite another session's notes. The scratchpad may hold task notes, source references and necessary excerpts, grill answers, findings, a draft plan, reviewer comments and responses, decisions, and unresolved questions. It is a working draft, not a replacement for `handoff` or `session-closeout`. Do not create a standalone implementation-brief artifact.

## Debate in the scratchpad

1. **Draft:** the author records the goal, scope and exclusions, constraints, proposed steps or slices, dependencies, alternatives and tradeoffs, assumptions, risks, verification/rollback ideas where relevant, and open questions. Cite consequential factual premises to source locations. Mark unknowns and proposed choices as such; do not convert grill answers or secondhand summaries into verified facts.
2. **Challenge:** give the declared challenge reviewer only the scratchpad and the necessary source excerpts to verify important claims, with provenance and access to originals where authorized and needed. Ask for concrete counterexamples, missing dependencies, conflicting requirements, unsafe sequencing, and untested assumptions. Record each numbered finding with its claim, category (**Observed contradiction** when inspected evidence conflicts, **Concern** for a plausible risk or prediction, or **Unsupported assertion** when adequate evidence is missing), source reference or explicit evidence gap, impact, and a proposed check or change. No fabricated citations or invented test results. A reviewer unable to verify a material premise must say so rather than endorsing it.
3. **Independent check (if available):** give the independent reviewer the scratchpad including the draft and challenge, plus only the necessary source excerpts to verify key claims. Ask it to assess both the plan and the challenge, including whether objections are supported or overstated and what either reviewer missed. Record its own numbered findings and limitations separately; do not collapse independent comments into the first reviewer's voice. Disclose if this pass was skipped or could not verify sources.
4. **Response:** the plan author answers each finding by ID in the same scratchpad: accept and revise the draft, reject with evidence, or leave open with the missing check/decision. Preserve the original criticism alongside the response; do not erase or silently mark disagreement resolved. If a revision changes a material premise, return the changed portion and necessary evidence to the affected reviewer when available, recording any follow-up. Stop cycling when the owner has enough to decide; do not manufacture consensus.
5. **Owner arbitration:** present the revised draft and a short ledger of accepted changes, contested findings, unsupported claims, unverified sources, and unresolved risks/questions. Ask the owner to decide contested choices explicitly; record each decision and who made it. Anything not resolved remains open with an owner/next check, not an implicit approval. State which reviewers actually participated and what they inspected. Only the owner can give the go-ahead; even a review with no blockers does not prove the plan safe.

## Stop boundary

Leave the draft, exchanges, decisions, and unresolved items together in the scratchpad for later use. Do **not** apply the draft to project documents, approve an LLD, implement code, create a PR, or write a separate implementation brief as part of this skill. A later authorized workflow can use the settled plan as input to a slice-scoped delegate brief; `session-closeout` handles durable write-backs and `handoff` handles a specific next task. For one-shot plan feedback use a plan-review workflow instead; `two-axis-review`, `debate-review`, and `babysit-pr` concern code changes or PRs, not this pre-implementation exchange.
