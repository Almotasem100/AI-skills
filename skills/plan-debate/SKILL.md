# Plan debate

Debate a plan before implementation. The working output is **one session scratchpad**, not an approved design or a new document of record. A clean debate is not proof of safety. Material unresolved disagreements or decisions are escalated to the owner. When the debate resolves within an already authorized workflow, return the settled plan to that workflow without creating a new approval gate; reviewers do not implement changes during review.

## Set up the session

1. Read the project's instructions and any scratchpad/closeout profile. Identify the proposed change, scope, plan-author role, challenge-reviewer role, any justified independent-review role, and owner. Resolve those roles through configured delegation lanes unless the owner explicitly chooses participants or the active model is itself configured for one of those roles. State participants and roles before dispatch; the orchestrator coordinates the exchange and must not present its own self-review as independent debate. Use routes within the current authorization and project rules. If a required role and any configured fallback are unavailable, disclose the capability gap; never silently substitute an unconfigured participant or claim a debate occurred.
2. Gather the ticket, requirements, slides, existing design/LLD, relevant project documents and source files needed to test important claims. Ask for missing or inaccessible material rather than treating a summary as proof. Follow project rules for sensitive material and external transmission: include only necessary, authorized excerpts, never secrets or customer data. Record provenance (file and line/section, slide number, ticket item, or a distinctive label for pasted text), and note which sources were actually inspected versus only reported by someone else.
3. Choose **one working scratchpad**. Reuse a project's designated session scratchpad only if its profile permits this debate content and reuse; preserve its format and existing entries. Otherwise create a separate temporary working file outside project repositories, at a location agreed with the owner when project rules do not specify one. Do not overwrite another session's notes. The orchestrator is the scratchpad's **only writer** because it owns the shared coordination state; this does not make the orchestrator the author of the plan or reviewer findings. Delegated roles return their own attributed outputs, and the orchestrator records or links those outputs without substantively rewriting them. Give each role the minimum useful context and canonical source access needed for its responsibility. A role that is authorized to inspect project sources may inspect those sources directly. When the shared scratchpad itself must remain read-only and the host cannot enforce that boundary, provide an immutable scratchpad or plan snapshot rather than its writable path. Do not freeze or copy unrelated session material merely because delegation occurred. Never claim a host-enforced access guarantee without evidence. The scratchpad may hold task notes, source references and necessary excerpts, grill answers, findings, a draft plan, reviewer comments and responses, decisions, and unresolved questions. It is a working draft, not a replacement for `handoff` or `session-closeout`. Do not create a standalone implementation-brief artifact.

## Debate in the scratchpad

1. **Draft:** the author records the goal, scope and exclusions, constraints, proposed steps or slices, dependencies, alternatives and tradeoffs, assumptions, risks, verification/rollback ideas where relevant, and open questions. Cite consequential factual premises to source locations. Mark unknowns and proposed choices as such; do not convert grill answers or secondhand summaries into verified facts.
2. **Challenge:** give the challenge reviewer the current plan plus only the task context and source access needed to test important claims. If the reviewer may safely inspect canonical sources within the authorized scope, let it do so directly. Give the shared scratchpad read-only only when useful and enforceable; otherwise provide the relevant immutable plan/scratchpad snapshot rather than the writable record. Ask for concrete counterexamples, missing dependencies, conflicting requirements, unsafe sequencing, and untested assumptions. Require a separate Markdown response containing numbered findings, each with its claim, category (**Observed contradiction**, **Concern**, or **Unsupported assertion**), source reference or explicit evidence gap, impact, and proposed check or change. No fabricated citations or invented test results. A reviewer unable to verify a material premise must say so rather than endorsing it.
3. **Independent check (if available):** give the independent reviewer read-only scratchpad access only if the host enforces it; otherwise provide an immutable plan snapshot and, if useful, the other reviewer's returned Markdown report plus necessary source excerpts. Ask it to assess the plan and prior findings, including whether objections are supported or overstated and what was missed. Require a separate Markdown response (or authorized `minipad.md`) with its findings and limits; do not collapse its comments into the first reviewer's voice. Reviewers may be dispatched in parallel when the owner has authorized both. The orchestrator may relay outputs for a response round without taking a substantive side; it remains the sole scratchpad writer and records attribution. Disclose if a pass was skipped or could not verify sources.
4. **Response:** the plan author returns an answer for each finding by ID—accept and revise, reject with evidence, or leave open with the missing check/decision. If the author is delegated, route the findings back to that same author role; do not have the orchestrator recreate the author's response. Preserve returned reports and attribution; do not erase criticism or silently mark disagreement resolved. The orchestrator records attribution and state and may relay subsequent rounds without taking a substantive side. If a revision changes a material premise, send only the revised plan and necessary evidence to the affected reviewer within the current authorization. Stop cycling when additional rounds no longer change a material issue or when a real owner decision is required; do not manufacture consensus.
5. **Owner arbitration:** escalate only material contested choices, unresolved requirements, consequential unsupported assumptions, or decisions that exceed the current authorization envelope. Present those items with the competing positions and evidence and ask the owner to decide. Record each owner decision and who made it. Findings resolved by the plan author within the authorized scope do not require owner approval merely because they passed through debate. Anything materially unresolved remains open with an owner/next check, not an implicit approval. State which reviewers actually participated and what they inspected. A review with no blockers does not prove the plan safe.

## Stop boundary

Leave the draft, exchanges, decisions, and unresolved items together in the scratchpad for later use. This skill does not itself implement code, approve an LLD, create a PR, or perform durable project-document write-backs. Return the settled plan, participant ledger, unresolved items and evidence limits to the calling workflow. If that workflow is already authorized to continue and no blocker or owner-requested checkpoint remains, the orchestrator may proceed to its next appropriate stage without requesting another approval. `session-closeout` handles durable write-backs and `handoff` handles a specific next task. For one-shot plan feedback use a plan-review workflow instead; `two-axis-review`, `debate-review`, and `babysit-pr` concern code changes or PRs, not this pre-implementation exchange.
